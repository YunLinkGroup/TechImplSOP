| 维度        | Memcached                                                    | Redis                                                        | ▶Memcached 视角（只谈自身）                                  |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 数据模型    | 纯 key-value，**value 只能是 blob**；无命名空间、无数据类型  | 6 种基础数据结构（string/list/set/zset/hash/stream）+ RedisJSON 等模块 | 当年只为**加速动态 Web 页面**而生，能 O(1) get/set 即可；拒绝数据类型换来**极简协议 + 零解析开销**。 |
| 持久化      | **完全不支持**；重启即空                                     | RDB、AOF、混合持久化；可配置 fsync 策略                      | 代码里直接没有文件 I/O，**重启清零被视为特性而非缺陷**，换来两点：① 内存分配器可以做成“ slab + 预分配”，无需考虑文件句柄；② 运维模型极简：机器掉电=自动清垃圾。 |
| 线程/CPU    | 经典版**单线程多路复用**（1 个 worker + 1 个 stat）；1.6 才引入 IO 线程，但命令执行仍是单线程 | 6.0 前网络+命令主线程合一；6.0 后可把网络 I/O 多线程化，**命令执行依旧单线程** | 坚持“一条线程跑一切”近 20 年，**无锁、无上下文切换、CPU 缓存友好**，但也把“热 key 打爆 CPU” 的锅扣在自己头上——这是 Memcached 性能天花板最常见的死因。 |
| 内存管理    | **固定大小 slab class**＋slab 内 chunk 大小阶梯式增长；**无碎片整理**，只能 LRU 踢老数据 | 打包成 jemalloc 的 malloc/free；支持 **active-defrag** 运行时整理碎片 | slab 机制让 1 MB value 与 1 KB value 井水不犯河水，**分配释放 O(1)**；代价是“**内存放大**”——平均浪费 25 %（worst case 50 %）且永远无法靠压缩解决。 |
| 高可用/集群 | **无内置集群**；客户端一致性哈希分片；**无主从、无哨兵**     | 原生 Cluster（16384 slot）、主从 + Sentinel、Redis Raft      | 一开始就把自己定位为“**分布式里的本地缓存**”，高可用交给客户端或上层代理（magent、twemproxy）；**节点之间彼此不通信**，协议里根本没有节点 ID 概念——简单到极致，但也意味着**故障切换要全网客户端同时刷新哈希表**，瞬断明显。 |
| 功能特性    | 只有 get/set/add/cas/incr/decr/flush\_stats；**无发布订阅、无 Lua、无事务** | 发布订阅、Lua 脚本、事务、HyperLogLog、Bitmap、Stream、RedisSearch/JSON/Graph 等模块 | 功能列表短到可以背下来，**协议层 16 字节头部定长**，解析用 C 宏就能完成；拒绝“功能蔓延”换来**极低的客户端延迟 P99**。 |
| 性能边界    | 单实例 100 K~200 K qps（value 1 KB）；**热 key 单线程打满即封顶** | 单实例 80 K~150 K qps（不开 IO 线程）；**多 IO 线程后可到 120 W qps** | 性能曲线“**横着走**”——一旦 CPU 跑满 1 核就再无法提升；所以线上标配是“**一机多实例**”+ 客户端一致性哈希，靠“堆进程”而不是“堆核心”扩容。 |
| 典型场景    | ① 纯 KV 缓存且可接受重启丢数据；② 只读比例极高、写很少；③ 作为**二级缓存**挡在 Redis 之前抗热点 | 需要数据结构、持久化、复制、发布订阅、排行榜、计数器、流式消息等 | Memcached 最成功的用法：**“把最热 1 % 的 key 再缓存一层”**——利用它内存便宜+零维护成本，给 Redis 或 DB 挡枪；一旦业务需要“除缓存外再干点别的”，它立即出局。 |
